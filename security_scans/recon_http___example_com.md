## 1. خلاصهٔ وضعیت فعلی

1. **پوشش زیر دامنه‌ها** نسبتاً کامل است؛ تمام نقاط ورودی عمومی و چند نقطهٔ داخلی (dev, lab) کشف شده‌اند.  
2. **فاصلهٔ اطلاعات** از فاز فوزی (FFUF) نشان می‌دهد که مسیرهای عمومی یا فایل‌های پیش‌فرض (مانند `admin`, `login`, `phpinfo.php` و غیره) در دسترس نیستند یا به‌خوبی محافظت شده‌اند.  
3. برخی زیر دامنه‌ها (مانند `dev` و `emudhra‑lab`) معمولاً باید دسترسی‌های محدود داشته باشند؛ وجود آنها در DNS عمومی می‌تواند اطلاعات حساس را به مهاجمان بدهد، مخصوصاً اگر به‌درستی پیکربندی نشوند.

## 2. تجزیه و تحلیل ریسک

| زیر دامنه | ریسک احتمالی | نکات کلیدی برای بررسی |
|----------|--------------|------------------------|
| **support.example.com** | **متوسط** – اگر سامانه پشتیبانی به‌صورت فرم‌های وب یا سیستم تیکت‌گذاری باشد، ممکن است فهرست خطاها یا اطلاعات داخلی (مانند شماره‌های سریال، API keys) در پاسخ‌ها فاش شود. | بررسی وجود API یا رابط‌های REST، ارزیابی نرخ پاسخ‌های HTTP (500/401/403) برای یافتن نقاط ضعف. |
| **m.example.com** | **پایین تا متوسط** – نسخهٔ موبایل گاهی حاوی فایل‌های JavaScript یا منابع کم‌امنیتی می‌شود. | بررسی وجود `*.js`، `manifest.json`، و مسیرهای `api/` مرتبط با برنامهٔ موبایل. |
| **www.example.com** | **متوسط تا بالا** – وب‌سایت اصلی معمولاً بیشترین سطح دسترسی عمومی را دارد؛ ممکن است به‌صورت مستقیم یا از طریق CMS دارای آسیب‌پذیری باشد. | اسکن دقیق‌تر (Nikto, OWASP ZAP) برای کشف صفحات admin، پارامترهای ورودی، و سرآیندهای امنیتی. |
| **emudhra‑lab.example.com** | **متوسط** – محیط آزمایشی ممکن است ابزارها یا دیتابیس‌های آزمایشی بدون محدودیت داشته باشد. | بررسی وجود صفحهٔ index، دسترسی به سرویس‌های Docker/K8s، یا endpointهای API تستی. |
| **dev.example.com** | **بالا** – اگر این محیط به‌صورت عمومی در دسترس باشد، می‌تواند شامل کد منبع، تنظیمات دیتابیس، یا کلیدهای API باشد. | تست دسترسی به `.git/`, `config/`, `env/`, `phpinfo.php`، و هر مسیر پیش‌فرض توسعه‌ای. |
| **products.example.com** | **متوسط** – ممکن است لیست محصولاتی داشته باشد که شامل URLهای API یا اسناد فنی باشد. | بررسی مستندات API، پارامترهای query، و امکان enumeration محصولات. |

## 3. توصیه‌های امنیتی (به زبان فارسی)

1. **محدودسازی دسترسی به زیر دامنه‌های داخلی**  
   - برای `dev.example.com` و `emudhra‑lab.example.com` از **VPN** یا **IP‑whitelisting** استفاده کنید. اگر این محیط‌ها نیازی به دسترسی عمومی ندارند، DNS را به‌صورت **private** یا **internal** تنظیم کنید.  
   - اضافه کردن **HTTP Authentication** یا **Basic Auth** به این زیر دامنه‌ها می‌تواند لایهٔ ابتدایی محافظت را فراهم کند.

2. **بهبود پیکربندی وب‌سرور**  
   - اطمینان حاصل کنید که **directory listing** غیرفعال باشد (`Options -Indexes`).  
   - هدرهای امنیتی مانند `X‑Content‑Type‑Options: nosniff`, `X‑Frame‑Options: SAMEORIGIN`, `Content‑Security‑Policy` و `Strict‑Transport‑Security` به‌درستی تنظیم شوند.  
   - استفاده از **TLS 1.2+** و حذف پشتیبانی از cipherهای ضعیف.

3. **اسکن دقیق‌تر**  
   - برای هر زیر دامنه یک اسکن جامع با ابزارهای **Nikto**, **OWASP ZAP**, **Burp Suite** یا **Nessus** انجام دهید.  
   - از **Wordlist**های بزرگتر برای FFUF (مانند `SecLists/Discovery/Web-Content`) استفاده کنید تا مسیرهای مخفی یا APIهای داخلی را کشف کنید.  
   - تست **parameter fuzzing** روی پارامترهای GET/POST برای کشف تزریق (SQLi, XSS, command injection).

4. **مانیتورینگ و لاگ**  
   - لاگ‌های وب‌سرور (access و error) را برای درخواست‌های مشکوک (مثلاً مسیرهای `/admin`, `/login`, `/phpinfo.php`) بررسی و به‌صورت خودکار با یک SIEM یا ابزار تحلیل لاگ نظارت کنید.  
   - استفاده از **Rate Limiting** برای جلوگیری از حملات brute‑force یا enumeration.

5. **به‌روزرسانی منظم**  
   - اطمینان حاصل کنید که تمام سرویس‌های وب (Apache/Nginx/Node/etc.) و فریم‌ورک‌های استفاده‌شده (CMS, frameworks) به آخرین نسخهٔ پایدار به‌روزرسانی شده باشند.  

6. **ارزیابی DNS**  
   - بررسی رکوردهای **CNAME**, **MX**, **TXT** (مانند SPF/DKIM) برای اطمینان از عدم افشای اطلاعات حساس.  
   - حذف یا مخفی‌سازی رکوردهای **subdomain delegation** که نیازی به آن‌ها ندارید.

7. **آموزش تیم‌های داخلی**  
   - برای تیم‌های توسعه و پشتیبانی آموزش‌های امنیتی (Secure Coding, OWASP Top 10) ارائه کنید تا از بروز آسیب‌پذیری در کد منبع جلوگیری شود.  

---

## 4. گام‌های پیشنهادی برای ادامهٔ تحقیق

1. **جمع‌آوری هدرهای HTTP** برای تمام زیر دامنه‌ها (با ابزار `curl -I` یا `httpx`).  
2. **اسکن پورت** با `nmap` برای شناسایی سرویس‌های غیر HTTP (مثلاً SSH, RDP, MySQL) که ممکن است به‌صورت عمومی باز باشند.  
3. **استفاده از ابزارهای Subdomain Takeover** (مثل `subjack`, `subzy`) برای بررسی اینکه آیا برخی زیر دامنه‌ها به سرویس‌های دیگر (S3, Heroku, GitHub Pages) اشاره می‌کنند و می‌توانند تصاحب شوند.  
4. **فروش داده‌های WHOIS** برای بررسی تاریخچهٔ ثبت دامنه، تغییرات مالکیت و اطلاعات تماس.  
5. **بررسی SSL/TLS** با `testssl.sh` یا `SSL Labs` برای کشف ضعف‌های رمزنگاری.

### نتیجه‌گیری

بررسی اولیهٔ DNS نشان می‌دهد دامنهٔ `example.com` دارای زیر دامنه‌های عمومی و داخلی است. عدم وجود خروجی FFUF ممکن است به‌دلیل محافظت مناسب یا تنظیمات فیلتر باشد، اما برای اطمینان بهتر است از لیست‌های مسیر پیشرفته‌تر استفاده شود. تمرکز اصلی باید بر روی ایزوله‌سازی زیر دامنه‌های توسعه/آزمایشی (`dev`, `emudhra‑lab`) و انجام اسکن‌های عمیق‌تر بر روی وب‌سایت اصلی (`www`, `support`) باشد. اجرای توصیه‌های بالا می‌تواند سطح امنیتی کلی دامنه را به‌طور چشمگیری ارتقا دهد.  

*این تحلیل بر پایه اطلاعات در دسترس (Subfinder) و عدم وجود داده‌های FFUF انجام شده است؛ برای ارزیابی کامل‌تر، جمع‌آوری داده‌های بیشتر (پروتکل‌های دیگر، اسکن پورت، و غیره) ضروری می‌باشد.*
